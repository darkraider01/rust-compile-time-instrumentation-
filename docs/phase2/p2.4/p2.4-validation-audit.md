# P2.4 Validation Audit and Production-Orchestration Record

**Scope:** P2.4 work through Issue #6.  This is a historical engineering record,
not an implementation plan or a claim that the remaining work has been completed.

## 1. Executive Summary

Issue #3 completed its intended **R-4 experimental spike**: controlled native
OpenTelemetry `--extern` injection is feasible.  The R-4 integration fixture proves
that an exact Cargo-reported artifact can be injected into an instrumented dependency
without changing its source or manifest.  It also supports the selected Hybrid
Fallback architecture:

- native OpenTelemetry when an exact, safe artifact is available; and
- Tier-2 C-ABI otherwise.

Issue #5 deterministic async context propagation is implemented and validated.
Issue #6 `tokio::spawn` call-site context propagation is implemented and validated
for native units.  These results remain valid after restoring the branch to its last
known sound state.

The audit established a separate productionization gap: ordinary `cargo instrument`
execution currently does not safely acquire the native R-4 artifact before wrapper
compilation.  P2.4 is therefore not yet fully production-hardened.  This does not
invalidate the spike:

```text
R-4 mechanism feasibility       PROVEN
R-4 controlled integration      PROVEN
R-4 production orchestration    UNRESOLVED
```

Status vocabulary in this record:

- **PROVEN** — directly demonstrated by retained tests or implementation.
- **IMPLEMENTED BUT NOT PRODUCTION-REACHABLE** — code exists, but ordinary CLI
  orchestration does not reach it safely.
- **PARTIALLY VALIDATED** — important paths are tested but a material coverage or
  identity condition remains absent.
- **UNRESOLVED** — no safe production design has been retained.
- **HYPOTHESIS / FUTURE INVESTIGATION** — a possible direction, not evidence.

## 2. Original P2.4 Audit

### Critical

None found.

### High

#### H1 — Native R-4 injection is not reachable through the normal CLI workflow

**Verified current repository fact.** `SessionPlan::add_r4_artifacts_from_cargo_json`
captures Cargo-authoritative `compiler-artifact` messages.  The ordinary CLI in
`cargo-instrument/src/main.rs`, however, creates its session with
`SessionPlan::build_from_metadata`.  That metadata-only session leaves
`r4_native_otel_artifacts` empty.  The controlled R-4 test performs its own
artifact-producing Cargo pre-pass and explicitly populates a session.

Consequently, an ordinary wrapper invocation cannot select `NativeOtelEmitter` for a
dependency through that native path.  Issue #3 remains legitimately closed because it
was an experimental spike; the missing normal-CLI integration is a later
productionization problem, not a retroactive failure of the spike.

#### H2 — Resolved OpenTelemetry features are captured but not validated at selection — RESOLVED

**Previously verified repository fact, now resolved.** `R4NativeOtelArtifact::resolved_features`
is recorded directly from the authoritative Cargo `compiler-artifact` message.
`SessionPlan::r4_native_otel_artifact_for` previously compared only package identity, target,
and profile.

Investigation proved **Outcome A (feature mismatch is reachable)**: when a workspace target
selects an `opentelemetry` feature set lacking `"trace"` (e.g. `features = ["metrics"]`), Cargo
resolver v2 compiles `opentelemetry` for that target invocation without `"trace"`. Under previous
code, `dep_shared` selected `NativeOtelEmitter`, injected `--extern opentelemetry`, and failed to
compile with `error[E0433]: cannot find trace in opentelemetry`.

**Resolution:**
1. `add_r4_artifacts_from_cargo_json` captures exact resolved features from Cargo `compiler-artifact`
   messages.
2. `r4_native_otel_artifact_for` strictly enforces that the selected artifact contains the
   mandatory `"trace"` feature and satisfies all expected dependency features in
   `r4_expected_features_by_dependency`.
3. Application crate emitter selection in `wrapper.rs` verifies `package_has_otel_trace(crate_name)`,
   falling open to `TrampolineEmitter` (if `otel-shim` is present) or S11 fail-open if `"trace"` is
   absent.
4. On any feature mismatch, selection fails open to Tier-2 C-ABI without build breakage, source
   mutation, or manifest alteration. Fully verified by `r4_h2_feature_safety_tests.rs`.

#### H3 — A `--extern tokio` binding name does not prove Cargo package identity

**Verified current repository fact.** The wrapper treats a rustc extern binding named
`tokio` as the cheap gate for spawn discovery.  That establishes only the binding name;
a Cargo dependency rename can expose a non-Tokio package as `tokio`, for example:

```toml
tokio = { package = "some-other-package", ... }
```

Safe automatic rewriting should eventually verify the underlying Cargo package identity
and fail open when it cannot be established.

## 5. Evidence That Remains Valid

### R-4 controlled integration proof — PROVEN

```bash
cargo test -p cargo-instrument --test r4_extern_injection_tests -- --ignored --nocapture
```

**Current result: PASS** (rerun on the restored branch during this record's creation).

This proves native OpenTelemetry `--extern` injection can compile; an instrumented
dependency need not declare OpenTelemetry; exact Cargo-reported paths can be consumed;
sync spans export; async instrumentation and parent-child relationships work; Tokio
spawn propagation works in this fixture after Issue #6; and dependency source/manifests
remain untouched.  The controlled resolver and fallback tests also function.

It does **not** prove automatic native artifact acquisition in ordinary CLI use, safe
pre-pass/final-build orchestration, or complete cross-platform production support.

### Issue #5 deterministic migration proof — PROVEN

The proof polls the same pending `Send` future on OS thread A, obtains `Pending`,
transfers it, and polls it to `Ready` on OS thread B.  Context is reattached on every
poll.  This deterministic construction proves the intended migration property without
relying on Tokio to happen to migrate a task randomly.

### Issue #6 spawn propagation — PROVEN for native units

The implementation captures context at the `tokio::spawn` call site before scheduling,
uses `FutureExt::with_context`, checks TraceId and parent SpanId, creates no synthetic
task span, and is scoped to native emitters; Tier-2 behavior remains unchanged.  Spawn
recognition is conservative.  Existing hardening includes exact generated-wrapper
idempotence recognition and file-wide lexical-shadow suppression for modules, imports,
extern aliases, structs, enums, unions, traits, type aliases, and type generic
parameters named `tokio`.

**Correction to the earlier remaining-work phrasing:** the type-namespace shadow cases
are already implemented on the restored branch.  Cargo package identity, not those
lexical forms, is the remaining spawn-recognition gap.

## 6. Productionization Attempt After the Audit

After the audit, an implementation was attempted to populate native R-4 artifacts in
the real CLI session using a wrapper-disabled Cargo JSON artifact pre-pass.  The attempt
was **not retained**.  The branch was restored to the prior sound state; no experimental
production code remains and no productionization commit was pushed.

The work was stopped because the two investigated orchestration variants exposed an
unresolved Cargo/Rust identity and freshness problem rather than a safe incremental
change.

## 7. Discovered Cargo/Rust Constraint

### Strategy A — isolated target-directory pre-pass

```text
run Cargo pre-pass in isolated target dir
→ capture OpenTelemetry compiler-artifact JSON
→ inject resulting rlib into real instrumented build
```

**Previous empirical observation.** The isolated pre-pass compiled OpenTelemetry and
upstream dependencies in a different Cargo/rustc build graph.  Its artifact could not
be safely mixed with crates compiled in the real graph; observed compiler failures
showed incompatible crate/upstream-crate identity.  Rust crate compatibility includes
compilation and upstream metadata beyond a path and crate name.

**Conclusion:** isolated-target acquisition is **not currently considered safe**.

### Strategy B — same real target-directory pre-pass

```text
run normal Cargo build/pre-pass in real target dir
→ capture exact compatible OpenTelemetry artifact
→ run wrapper-enabled build
```

**Previous empirical observation.** This produced a compatible OpenTelemetry artifact,
but also compiled dependency units.  Cargo subsequently treated those units as fresh and
reused the uninstrumented artifacts, bypassing the wrapper for the dependencies that
needed instrumentation.

**Conclusion:** same-target pre-pass produces compatible identity but can poison Cargo
freshness for units that must later pass through `RUSTC_WRAPPER`.

## 8. Current Core Architectural Problem

> Obtain the exact Cargo-built OpenTelemetry artifact from the same effective build
> identity while still guaranteeing that selected dependency compilation units are
> subsequently recompiled through `RUSTC_WRAPPER`.

This is the central unresolved production-orchestration problem for native R-4.  It is
not claimed impossible.

## 9. Candidate Future Directions

These are **HYPOTHESIS / FUTURE INVESTIGATION**, not proven recommendations.

### Candidate A — same-target pre-pass plus supported selective invalidation

```text
same target Cargo pre-pass
→ capture authoritative OpenTelemetry artifact
→ selectively invalidate dependency units
→ wrapper-enabled final build
```

`cargo clean -p <package>` is a possible supported mechanism to investigate.  Cargo
operates across target/host units, profiles, features, build scripts, proc macros, and
multiple targets; package-level clean may remove too much or be unable to express the
precise instrumentation-unit set.  It needs empirical validation.

### Candidate B — single-build coordination

One real Cargo build could capture `compiler-artifact` messages as OpenTelemetry becomes
available and share them with wrapper processes dynamically.  Unresolved concerns are
parallel unit scheduling, a dependency beginning before OpenTelemetry exists, wrapper
waiting, and potential deadlock or jobserver interaction.

### Candidate C — other stable-Cargo orchestration

Investigate whether stable Cargo offers a supported way to build/capture the exact
OpenTelemetry unit, retain it, force only selected dependencies to recompile, and avoid
manual Cargo fingerprint manipulation.

## 14. H1 Production-Orchestration Validation Update (2026-09-21)

This section records post-audit evidence. It supersedes this record's H1
production-status entries only; it does not close H2, H3, or the broader P2.4
hardening work.

### Implemented orchestration

Ordinary cargo instrument build and cargo instrument run now:

1. construct metadata using the invocation's resolution flags, including
   --offline;
2. run a wrapper-disabled, same-target Cargo JSON pre-pass (run is represented
   by an equivalent build pre-pass because Cargo does not accept
   --message-format for run);
3. capture the exact Cargo-reported OpenTelemetry rlib in the per-invocation
   session plan;
4. invalidate only target units that the pre-pass actually rebuilt and that the
   wrapper is expected to instrument, covering both native and Tier-2 policy;
5. preserve the selected artifact and its Cargo dependency closure, unless that
   closure conflicts with a required instrumented unit; and
6. run the final Cargo invocation with RUSTC_WRAPPER.

Malformed JSON falls back to conservative full selected-unit invalidation.
Pre-pass failures after partial compilation invalidate the rebuilt selected
units before the final build. Selective-clean ambiguity or failure terminates
with an actionable orchestration error rather than allowing potentially
uninstrumented artifacts to be reused. No fingerprint manipulation, source
mutation, filename globbing, or cross-invocation session cache is used.

### Corrected defects

- A relative --manifest-path pre-pass must run from the original invocation
  directory, not from the manifest directory.
- Metadata probes must forward Cargo resolution flags; otherwise an offline
  command can incorrectly attempt registry access and lose the session plan.
- cargo run --message-format is invalid; native artifact acquisition uses
  cargo build and leaves execution to the final run.
- Cargo's package clean command on the validated toolchain ignores
  source/version qualifiers. Multiple selected packages with the same name
  are therefore rejected for native orchestration instead of being cleaned
  ambiguously.
- Cargo's `fresh` compiler-artifact status is not treated as proof that a
  dependency was transformed. The wrapper writes a marker only after a
  successful compile from a mirrored source tree; the marker is keyed by the
  normalized target name and Cargo's exact `extra-filename` artifact hash.
  Fresh artifacts must have the matching marker at least as new as every
  reported artifact, otherwise the package is selectively invalidated. The
  former crate-wide marker is not trusted.

### Production evidence

New real-CLI regression coverage proves:

- automatic native artifact acquisition without a manually populated session;
- wrapper interception and exact native --extern opentelemetry=<Cargo rlib>
  injection for a dependency with no OpenTelemetry manifest dependency;
- native dependency mirror output and correctly parented exported spans;
- a mixed graph in which dep_native receives native R-4 output while dep_tier2
  intentionally receives Tier-2 C-ABI output, with both spans exported under
  the application parent;
- recovery from a pre-pass that compiled dependencies then failed in the
  application: both dependencies are recompiled through the wrapper using
  Tier-2 fallback rather than silently reused;
- source, manifest, and registry-source-cache byte preservation; and
- successful cold, repeat, incremental, and clean rebuild behavior.

Validation was run with the cached registry in offline mode because several
pre-existing temporary-fixture tests otherwise attempt unavailable network
resolution. cargo fmt --check, workspace Clippy with -D warnings, and the full
offline workspace test suite passed. The focused H1 CLI suite passed nine
active tests; the older controlled R-4 spike remains explicitly ignored by
default and was separately run successfully. A dedicated freshness regression
also proves that a legacy crate-wide marker cannot certify a fresh artifact and
that the exact transformed-unit marker is accepted.

### H2 Resolution — Feature-Safe Native OpenTelemetry Selection

#### Reachability Investigation (Outcome A Confirmed)

Under Cargo resolver v2, feature unification operates only across the packages included in a given build invocation. When building a specific target package (`cargo instrument run -p root_metrics`), Cargo compiles `opentelemetry` with only the features demanded by that target root's dependency tree. If that root specifies `default-features = false, features = ["metrics"]`, the compiled OpenTelemetry `.rlib` lacks the `"trace"` module required for native instrumentation.

Previously, `r4_native_otel_artifact_for` selected artifacts based solely on `(package_id, target, profile)` without validating resolved features, leading to rustc compile failures (`cannot find trace in opentelemetry`) when injecting `--extern opentelemetry` into shared dependencies.

#### Implementation

1. **Authoritative Feature Extraction**: `add_r4_artifacts_from_cargo_json` parses the `features` array directly from Cargo's `compiler-artifact` JSON message, rather than relying on workspace-wide `cargo metadata` nodes.
2. **Strict Selection Validation**: `SessionPlan::r4_native_otel_artifact_for` validates that:
   - The candidate artifact contains the mandatory `"trace"` feature.
   - The candidate artifact satisfies all features specified in `r4_expected_features_by_dependency`.
3. **Application Crate Protection**: `wrapper.rs` verifies `package_has_otel_trace(crate_name)` before applying `NativeOtelEmitter` to application crates, falling open to `TrampolineEmitter` (if `otel-shim` is linked) or S11 fail-open.
4. **Clean Tier-2 Fail-Open**: Any feature mismatch returns `Err`, allowing the wrapper to emit a non-fatal diagnostic and safely fall back to the Tier-2 C ABI.

#### Test Evidence (`r4_h2_feature_safety_tests.rs`)

1. `test_h2_adversarial_feature_metrics_only_lacks_trace`: Proves that when an application targets `opentelemetry` with only `metrics`, native injection fails open to Tier-2 C ABI, compilation succeeds, and the binary executes cleanly.
2. `test_h2_valid_native_artifact_selected`: Proves that when `trace` is present, native R-4 injection is selected.
3. `test_h2_workspace_feature_unification_enables_native`: Proves that Cargo resolver v2 feature unification across workspace targets properly enables native injection.
4. `test_h2_target_mismatch_fails_open`: Target mismatch cleanly falls open.
5. `test_h2_profile_mismatch_fails_open`: Profile mismatch cleanly falls open.
6. `test_h2_multiple_otel_versions_incompatible_roots`: Conflicting OpenTelemetry versions across roots fall open to Tier-2.

All 6 H2 tests, 13 H1 production orchestration tests, and the entire workspace test suite pass without regression.
