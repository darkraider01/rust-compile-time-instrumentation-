## 13. Technical Risks


Format: **Risk → Severity → Why → Mitigation.**
Severity: **Critical** (kills the project or silently corrupts user programs) · **High** (major rework or unusable output) · **Medium** (painful, workable) · **Low** (annoyance).

| # | Risk | Severity | Why | Mitigation |
| --- | --- | --- | --- | --- |
| R1 | **Cargo caching serves an uninstrumented artifact** | **Critical — [Fact, confirmed by direct experiment, not hypothetical]** | Verified on Cargo 1.97.1: `RUSTC_WRAPPER`/`RUSTC_WORKSPACE_WRAPPER` do **not** participate in Cargo's rebuild fingerprint. Toggling the wrapper on for an already-built crate produces zero recompilation and the wrapper is never invoked for the actual crate compile. This is not a narrow edge case — it is the default steady-state behaviour of a plain `cargo build`. See [Appendix B](appendix-b-verification-log.md) item 2 | **[Revised — see [Appendix C.3](appendix-c-adversarial-review.md)]** The original `RUSTFLAGS`-hash mitigation works but is destructive: it is a global flag, so it evicts the cache of every crate in the workspace and dependency graph (not just the ones we touch), and as an environment variable it clobbers `[build] rustflags` in `.cargo/config.toml` without merging, silently dropping the user's own sanitizer/target/link flags. **Confirmed working replacement**: build into an isolated `--target-dir` (e.g. `target/instrumented`) whenever instrumentation is active. There is no stale artifact to reuse in a fresh directory, so the wrapper always runs, and the user's default `target/` cache and `RUSTFLAGS`/config are left untouched. This must ship from the tool's first commit. Additionally emit a startup log line stating instrumentation is active, and a test that fails if it is absent |
| R2 | **Rust compiler / language instability** | **Low** for Architecture A | A stays on stable and only needs `syn` to parse the syntax. New syntax lands in `syn` releases, not in our code | Track `syn`. Fail *open* — an unparseable file is compiled unmodified with a warning, never a hard error |
| R3 | **Nightly dependency** | **Critical, if we take Architecture B** | `rustc_private` is permanently unstable; `rustc_plugin` treats nightly bumps as breaking changes **[Fact]**. Teams with MSRV policies cannot adopt it | Do not take Architecture B in Phase 1. If a MIR spike happens later, isolate it in a separate crate behind a feature flag, never on the default path |
| R4 | **Compiler-version compatibility** | **Medium** | Users run many Rust versions. Our generated code must compile on all of them | Generate conservative code only: no recently-stabilised syntax, no edition-specific constructs. Test against stable, stable-1, stable-2, stable-3 in CI |
| R5 | **Async instrumentation correctness** | **Critical** | The classic failure — holding a context-attach guard across `.await` — corrupts the thread-local context for *other* tasks, producing wrong traces globally rather than locally. A tool that does this is worse than no tool. **[Unchanged in substance by [Appendix D.2](appendix-d-maintainer-qa.md)]** The hazard is identical in both APIs; only the correct construct's name changes | **[Revised]** Never generate a guard held across an `.await`, in either API. For `async fn`, always wrap the future: `opentelemetry::trace::FutureExt::with_context`, which attaches on each `poll()` and detaches on yield — the maintainer-confirmed equivalent of `tracing::Instrument` (§5.3). Make MVP success criterion 4 (one span, duration ≈ 100 ms, context absent from the polling thread while suspended) and criterion 5 (isolation under worker-thread migration) blocking CI tests |
| R6 | **Macro interaction** | **High → Medium-high, [reframed, [Appendix D.2](appendix-d-maintainer-qa.md)]** | Attribute macro interaction with `#[async_trait]`, `#[tokio::main]`, `#[test]` etc. can produce confusing compile errors or silently wrong expansion. **Severity eased because the question changed**: we now splice statements into a function *body* rather than adding an attribute whose expansion order relative to other attributes matters ([§12.9](12-mvp-definition.md) O4). A body splice is invisible to attribute ordering; what it must survive is a macro that *rewrites the body it is spliced into* — `#[async_trait]` boxing the future being the main case | Test the macro matrix explicitly ([Appendix E](appendix-e-experiment-matrix.md) FE-11). Maintain an exclusion list of attributes we refuse to splice under, and skip rather than guess |
| R7 | **Generics and monomorphization: span explosion** | **Medium** | A generic helper instantiated 50 ways is one source site but many runtime call paths. Fine for span *count*, but a hot generic (e.g. a serde helper) can be called millions of times | Default to instrumenting only functions above a size threshold. **[Revised twice — [Appendix C.1](appendix-c-adversarial-review.md), then [Appendix D.2](appendix-d-maintainer-qa.md)]** `STATIC_MAX_LEVEL` was never a per-tool control (global and additive across the dependency graph), and with the move to the native OTel API it is not available at all. The kill switch is the dedicated `--cfg` gate on generated code, which deletes the call sites at compile time. Provide crate/module exclusion rules, and see [R23](13-technical-risks.md) for what the gate does *not* cover |
| R8 | **Runtime overhead** | **High** | Auto-instrumentation over-instruments by construction. Users will benchmark us against uninstrumented builds and leave | Conservative defaults (skip small fns, skip closures, never capture argument values). Document the dedicated `--cfg` kill switch prominently — it is now the *only* compile-time removal mechanism, since the native OTel API has no `STATIC_MAX_LEVEL` analogue ([R23](13-technical-risks.md)). Publish measured numbers. Ship a `--plan-only` mode so users see the span budget *before* they build |
| R9 | **Build-time overhead** | **Medium** | Parse + rewrite + print for every instrumented crate, plus reduced incrementality when rewritten sources change | Cache rewritten output keyed by (source hash, rule-set hash). Skip crates with no matching rules without parsing them at all. Measure and publish |
| R10 | **Duplicate instrumentation** | **High** | A function that is already instrumented, plus our injection, yields nested identical spans — traces become unreadable and users blame the tool | Detect and skip **both** forms: existing `#[instrument]`/`#[tracing::instrument]` attributes, **and** hand-written native OTel spans (`tracer.start`/`.with_context` in the body) — the second case became possible with [ADR-001](17-decision-records.md) and is the one a `tracing`-era design would have missed ([§12.9](12-mvp-definition.md) O5). Detect crates that already depend on `tracing` **or** `opentelemetry` and default to a more conservative rule set. Snapshot-test idempotence (§12.8, invariant S10) |
| R11 | ~~**Source location / diagnostic degradation, and comment loss**~~ **Substantially resolved — [Fact, see [Appendix C.6](appendix-c-adversarial-review.md)]** | If a compile error in rewritten source reports a line number from the rewritten file, users cannot debug it, and they will not trust the tool. A `syn`+`prettyplease` round-trip of a representative sample was measured to destroy all non-doc `//` comments (4/4 in the test) and fully reformat the entire file — not just the touched function (Appendix B item 7). | **Fixed by mechanism change, not by mitigation.** Following `cargo-mutants`' proven approach: `syn` is used only to locate targets and read `span().byte_range()`; the actual edit is a byte-range splice into the original UTF-8 buffer, not a parse→print round-trip. Comments, formatting, and line numbers are preserved exactly outside the inserted region — there is no `ra_ap_syntax` trade-off to make. Residual risk is now only the inserted lines themselves shifting line numbers *after* the insertion point within the same function, which is small and easy to test for directly. |
| R12 | **Debugging experience** | **High** | "My code does not compile under your tool" must be answerable in minutes, or nobody uses it | `--dump-rewritten` and `--plan-only` from day one. A `--dry-run` diff view. Log the exact `rustc` command line on failure |
| R13 | **OTel Rust API churn (traces still Beta)** | **Medium → High, [revised, [Appendix D.2](appendix-d-maintainer-qa.md)]** | **[Fact]** Traces API and SDK are Beta; breaking changes are expected. Severity rises because the reversal to native OTel generation removes the bridge crate that was absorbing this churn for us — we now generate against the Beta API directly | **[Mitigation rewritten — the old one was "generate `tracing` instead," which no longer applies.]** (a) Keep the generated-code surface deliberately narrow — span start, attribute set, status set, `with_context` — so a breaking change touches few constructs; (b) pin and test a specific `opentelemetry`/`opentelemetry_sdk`/`opentelemetry-otlp` version set and publish the matrix; (c) run the [§14.6](14-evaluation-plan.md) latest-version CI against `opentelemetry` itself, not only against instrumented libraries, so churn surfaces as a failing scheduled build rather than a user bug report; (d) the emitter seam (§11.4) keeps the blast radius to one component |
| R14 | ~~**`tracing-opentelemetry` version offset**~~ **CLOSED — [Appendix D.2](appendix-d-maintainer-qa.md)** | — | The risk was that a tool injecting both `tracing-opentelemetry` and `opentelemetry` hits their deliberate version offset. **We now inject neither `tracing` nor its bridge**, so the hazard cannot arise | No longer applicable. Retained for the record |
| R15 | ~~**#1571 resolves against `tracing`**~~ **CLOSED — [Appendix D.2](appendix-d-maintainer-qa.md)** | — | The risk was that OTel Rust standardises on its own API and our `tracing` output becomes non-idiomatic. #1571 resolved as "maintain both," and we have independently moved to the native API — which is what `docs/traces.md` recommends. The risk cannot fire in the direction it pointed | No longer applicable. The residual mirror-image risk (upstream shifts toward `tracing`) is covered by the same emitter seam |
| R16 | **Rewriting third-party sources** | **High — now Phase 1-relevant, not Phase 2-deferred** | Registry sources are read-only; crates use `include!`, `#[path]`, `build.rs`-generated modules, and elaborate `cfg`. **[Revised — see [Appendix C.2](appendix-c-adversarial-review.md)]** The cross-crate injection mechanism itself is now confirmed to work (extern `"C"` trampolines compile against an undeclared dependency on stable Rust), so this risk is no longer "does dependency instrumentation work at all" but specifically "does source-tree mirroring survive real-world crate layouts." The MVP's one-dependency slice (§12.1) is chosen to be simple enough to sidestep this for Phase 1; full dependency-graph coverage in Phase 2 will hit it directly | Mirror the full crate source tree (not just the entry file) into the isolated `--target-dir`, so relative `mod`/`include!`/`#[path]` resolution is preserved. Fail open per crate: if a dependency cannot be safely mirrored and spliced, compile it unmodified and say so in the plan. **[Added, [Appendix D.3](appendix-d-maintainer-qa.md)]** A rule pinned to a crate version rots silently as that crate releases — adopt `otelc`'s automated forward-compatibility CI (their issue #406 pattern): fetch each instrumented crate's latest stable release from the crates.io index on a schedule, run the instrumented build against it, and auto-file a tracking issue on breakage so a version range gets split deliberately rather than discovered by a user ([§14.6](14-evaluation-plan.md)) |
| R17 | **Security: telemetry exfiltration of secrets** | **Critical** | Recording arguments by default would send passwords, tokens, and PII to a telemetry backend that nobody audited | `skip_args` unconditionally in Phase 1 *(renamed from `skip_all` with the move off `tracing` — [§12.6](12-mvp-definition.md))*. Argument capture is opt-in, per-rule, and never a default. Specified as invariant **S7** ([§16.2](16-instrumentation-semantics.md)) and extended there to error values: an `Err` sets span status with **no description**, because a user error type's `Display` may itself carry credentials. Document this as a security property, not a limitation |
| R18 | **Instrumentation code panics** | **High** | A panicking `Debug` impl invoked from injected code turns a working program into a crashing one | Do not format user values (R17 already ensures this). Do not use `catch_unwind` as a crutch — it is a no-op under `panic=abort` |
| R19 | ~~**eBPF portability (future)**~~ **CLOSED — [Appendix D.4](appendix-d-maintainer-qa.md)** | — | Kernel floors, `CAP_BPF`/`CAP_SYS_PTRACE`/`CAP_NET_ADMIN`, lockdown mode, non-Linux platforms **[Fact]**. With the eBPF branch abandoned, these are no longer our constraints — **they are our market.** The platforms eBPF cannot reach (macOS, Windows, unprivileged containers, non-root) are exactly where compile-time instrumentation is the only option | Inverted from risk to positioning. Requirement that survives: the compile-time tool must never depend on eBPF being available — trivially satisfied now that no eBPF code will exist |
| R20 | ~~**The eBPF hypothesis (H2) is false**~~ **CLOSED — resolved upstream, [Appendix D.4](appendix-d-maintainer-qa.md)** | — | OBI maintainer Giuseppe Ognibene has a working prototype of Tokio async task reconstruction and context propagation in eBPF (OBI #1096), in final testing against task migration and pointer reuse. H2 is neither ours to validate nor ours to be wrong about | The §15.6 pivot condition fired and was executed: branch abandoned, no competing implementation, contribute to #1096 instead. Architecture A always had standalone value — that design choice is what makes this closure a scope clarification rather than a loss |
| R21 | ~~**Scope creep into eBPF during Phase 1**~~ **CLOSED — [Appendix D.4](appendix-d-maintainer-qa.md)** | — | The pull toward the most interesting part is real, but there is no longer an in-project eBPF branch to be pulled into | Boundary stands and is now absolute: no eBPF dependency enters this repository, in any phase. Time spent on eBPF goes to reviewing #1096 upstream, which is contribution, not scope creep |
| R22 | **`otelc` or the OTel Rust SIG ships this first** | **Low-medium** | Rust is the conspicuous gap on the zero-code list; someone will fill it | Not a reason to hurry into bad architecture. **[Strengthened, [Appendix D](appendix-d-maintainer-qa.md)]** We now have direct maintainer contact in `#otel-rust`, `#otel-go`, and `#otel-ebpf`, so this would surface as a conversation rather than a surprise release — the same channel that resolved D.2 and D.4. If it happens, contribute rather than compete |
| R23 | **No compile-time span removal in the native OTel API** | **Medium — [new, [Appendix D.2](appendix-d-maintainer-qa.md)]** | `tracing` compiles spans below `STATIC_MAX_LEVEL` out of the binary entirely. The native OTel API has no equivalent, so an instrumented build always carries its call sites. This was previously booked as an advantage of targeting `tracing` (§5.4 reason 4) and is a genuine regression from the reversal | The `--cfg` gate on generated code is the real kill switch and always was: [Appendix C.1](appendix-c-adversarial-review.md) established `STATIC_MAX_LEVEL` is global and additive, so it silenced users' own spans too and was never per-tool. A `--cfg`-gated splice is deleted at compile time regardless of which API it calls. **What genuinely changes** is the middle configuration — gate on, SDK not recording — which now costs a non-recording span instead of nothing. Measure it ([§12.8](12-mvp-definition.md) benchmarks, [Appendix D.6](appendix-d-maintainer-qa.md) D-Q3); if it is material, make the gate the documented default for release builds |
| R24 | **The cross-platform claim is untested** | **Medium — downgraded, [Appendix E](appendix-e-experiment-matrix.md) FE-7** | After [ADR-005](17-decision-records.md) closed the eBPF branch, the project's entire positioning is *"the platforms eBPF cannot reach"* — macOS, Windows, unprivileged containers, non-root. **[Fact — FE-7, run on WSL2 Linux]** The sync trampoline mechanism resolves and executes correctly on Linux/ELF/GNU-ld, in both debug and `lto=true`/`codegen-units=1`/`panic=abort` release profiles, with no anchoring flags — **the Linux leg is closed.** **macOS remains untested** — no local Mach-O environment; `ld64`'s dead-strip behaviour is the specific remaining worry, same shape as the LTO hazard in [§3.2.5](03-rust-compiler-pipeline.md) | Run FE-7's harness on a macOS CI runner (`macos-latest`) before the full cross-platform claim is made publicly. Until then, state "macOS" as design intent, not a demonstrated property — Linux and Windows are now demonstrated |
| R25 | **Async instrumentation may not cross the dependency boundary** | **Medium — downgraded, [Appendix E](appendix-e-experiment-matrix.md) FE-2** | The two mechanisms this document specifies were, as literally written, **incompatible for a dependency crate**: [§12.1a](12-mvp-definition.md) gives an instrumented dependency no Cargo edge to `opentelemetry`, and [§12.4](12-mvp-definition.md) generates `FutureExt::with_context`, a trait method on a type from that crate. **[Fact — FE-2, second round, after the first round's test was rejected for being unable to detect the failure it existed to check]** A hand-written `core`-only future wrapper — first-poll span start, attach/detach paired around each `poll()`, a validated detach token — was tested with a forced single-worker-thread interleaving that included a genuine positive control (a span created while a second task's context was live, confirmed parented to it) alongside the negative check (not parented to the first, suspended task). Both held; cancellation (drop mid-poll) also closed its span correctly. **The mechanism is demonstrated feasible.** What remains open: this wrapper has not been run through the real byte-range splicer into a real third-party crate, and not tested under LTO/`panic=abort` or on Linux | **Downgraded from "design, unproven" to "mechanism demonstrated, integration untested."** Remaining work: splice this wrapper into a real dependency via the actual [ADR-002](17-decision-records.md) mechanism (not hand-written), and re-run under the FE-1/FE-7 conditions (LTO, `panic=abort`, Linux) in combination, not in isolation |
| R26 | **`#![forbid(unsafe_code)]` crates cannot be instrumented** | **Medium — [new, Phase 0 completion audit]** | **[Fact]** Calling an `extern "C"` function is unsafe, and `forbid` — unlike `deny` — cannot be lifted by an inner `#[allow]`; the splice is a hard compile error (`E0453`). The attribute is common in the Rust ecosystem, and every crate carrying it is unreachable, which directly shrinks the coverage that distinguishes this tool from a wrapper ([§9.5](09-gap-analysis.md)) | Fail open: skip the crate, compile it unmodified, name the reason in the plan (invariant **S11**). **Never strip a user's own safety lint to instrument them.** Test the possible escape — `unsafe extern "C" { safe fn … }`, Rust 1.82+, callable without an `unsafe` block — to see whether it still trips the `unsafe_code` lint ([Appendix E](appendix-e-experiment-matrix.md) FE-3), then count the attribute's prevalence across a real corpus so the cost is a number rather than a worry |

**[Phase 0 completion audit, 2026-09-04]** R24–R26 were added when the [instrumentation semantics](16-instrumentation-semantics.md) were written out in full. All three are consequences of decisions already taken rather than new hazards — which is itself the finding: **writing the specification surfaced three risks that four rounds of prose review did not.** R25 in particular is a direct contradiction between two sections that had each been reviewed and accepted separately.
