## 13. Technical Risks


Format: **Risk → Severity → Why → Mitigation.**
Severity: **Critical** (kills the project or silently corrupts user programs) · **High** (major rework or unusable output) · **Medium** (painful, workable) · **Low** (annoyance).

| # | Risk | Severity | Why | Mitigation |
| --- | --- | --- | --- | --- |
| R1 | **Cargo caching serves an uninstrumented artifact** | **Critical — [Fact, confirmed by direct experiment, not hypothetical]** | Verified on Cargo 1.97.1: `RUSTC_WRAPPER`/`RUSTC_WORKSPACE_WRAPPER` do **not** participate in Cargo's rebuild fingerprint. Toggling the wrapper on for an already-built crate produces zero recompilation and the wrapper is never invoked for the actual crate compile. This is not a narrow edge case — it is the default steady-state behaviour of a plain `cargo build`. See [Appendix B](appendix-b-verification-log.md) item 2 | **Confirmed working mitigation**: pair every wrapper toggle / rule-set change with a synthetic `RUSTFLAGS` value derived from a hash of the active rule set + tool version — experimentally confirmed to force recompilation on every change. This must ship from the tool's first commit, not be treated as a later hardening pass. Additionally emit a startup log line stating instrumentation is active, and a test that fails if it is absent |
| R2 | **Rust compiler / language instability** | **Low** for Architecture A | A stays on stable and only needs `syn` to parse the syntax. New syntax lands in `syn` releases, not in our code | Track `syn`. Fail *open* — an unparseable file is compiled unmodified with a warning, never a hard error |
| R3 | **Nightly dependency** | **Critical, if we take Architecture B** | `rustc_private` is permanently unstable; `rustc_plugin` treats nightly bumps as breaking changes **[Fact]**. Teams with MSRV policies cannot adopt it | Do not take Architecture B in Phase 1. If a MIR spike happens later, isolate it in a separate crate behind a feature flag, never on the default path |
| R4 | **Compiler-version compatibility** | **Medium** | Users run many Rust versions. Our generated code must compile on all of them | Generate conservative code only: no recently-stabilised syntax, no edition-specific constructs. Test against stable, stable-1, stable-2, stable-3 in CI |
| R5 | **Async instrumentation correctness** | **Critical** | The classic failure — holding a span guard across `.await` — corrupts the thread-local span stack for *other* tasks, producing wrong traces globally rather than locally. A tool that does this is worse than no tool | Never generate a raw `span.enter()` guard in an `async fn`. Always generate the `#[instrument]` / `Instrumented`-future form. Make MVP success criterion 4 (busy≈0, total≈100 ms) a blocking CI test |
| R6 | **Macro interaction** | **High** | Attribute macro ordering with `#[async_trait]`, `#[tokio::main]`, `#[test]` etc. can produce confusing compile errors or silently wrong expansion | Test the common macro combinations explicitly (O4). Maintain an exclusion list of attributes we refuse to co-apply with, and skip rather than guess |
| R7 | **Generics and monomorphization: span explosion** | **Medium** | A generic helper instantiated 50 ways is one source site but many runtime call paths. Fine for span *count*, but a hot generic (e.g. a serde helper) can be called millions of times | Default to instrumenting only functions above a size threshold. Default span level `DEBUG`, so `STATIC_MAX_LEVEL` removes them in release unless asked for. Provide crate/module exclusion rules |
| R8 | **Runtime overhead** | **High** | Auto-instrumentation over-instruments by construction. Users will benchmark us against uninstrumented builds and leave | Conservative defaults (skip small fns, skip closures, `skip_all` for args). Document `STATIC_MAX_LEVEL` prominently. Publish measured numbers. Ship a `--plan-only` mode so users see the span budget *before* they build |
| R9 | **Build-time overhead** | **Medium** | Parse + rewrite + print for every instrumented crate, plus reduced incrementality when rewritten sources change | Cache rewritten output keyed by (source hash, rule-set hash). Skip crates with no matching rules without parsing them at all. Measure and publish |
| R10 | **Duplicate instrumentation** | **High** | A crate that already has `#[instrument]`, plus our injection, yields nested identical spans — traces become unreadable and users blame the tool | Detect existing `#[instrument]`/`#[tracing::instrument]` attributes and skip. Detect crates that already depend on `tracing` and default to a more conservative rule set. Snapshot-test idempotence (§12.8) |
| R11 | **Source location / diagnostic degradation, and comment loss** | **High — partly confirmed, not just anticipated** | If a compile error in rewritten source reports a line number from the rewritten file, users cannot debug it, and they will not trust the tool. **[Fact, confirmed by direct experiment]** A `syn`+`prettyplease` round-trip of a representative sample destroyed all non-doc `//` comments (4/4 in the test) and fully reformatted the entire file — not just the touched function — while an idempotent second pass changed nothing further. See [Appendix B](appendix-b-verification-log.md) item 7 | Preserve spans through the rewrite where possible. Evaluate a CST-based rewriter (`ra_ap_syntax`) that only inserts and never reflows, now that `syn`+`prettyplease`'s cost is quantified rather than assumed. Always write rewritten sources to a stable inspectable path. At minimum, document the comment-loss and full-reformat behaviour prominently — a user who sees their comments vanish without warning will distrust the tool regardless of whether the compiled output is correct |
| R12 | **Debugging experience** | **High** | "My code does not compile under your tool" must be answerable in minutes, or nobody uses it | `--dump-rewritten` and `--plan-only` from day one. A `--dry-run` diff view. Log the exact `rustc` command line on failure |
| R13 | **OTel Rust API churn (traces still Beta)** | **Medium** | **[Fact]** Traces API and SDK are Beta; breaking changes are expected | Generate `tracing` calls, not OTel calls, so churn is absorbed by `tracing-opentelemetry`. Pin a tested `(opentelemetry, tracing-opentelemetry)` version pair and document it |
| R14 | **`tracing-opentelemetry` version offset** | **Medium** | **[Fact]** Its version runs one ahead of `opentelemetry`'s; a tool that injects both will produce mismatches | Ship a tested compatibility matrix; validate at analysis time and fail with a clear message rather than a resolver error |
| R15 | **#1571 resolves against `tracing`** | **Medium** | If OTel Rust standardises on its own API, our generated code becomes non-idiomatic | The emitter seam (§11.4). Re-read #1571 before Phase 2 |
| R16 | **Rewriting third-party sources (Phase 2)** | **High** | Registry sources are read-only; crates use `include!`, `#[path]`, `build.rs`-generated modules, and elaborate `cfg` | Prototype early (O3). Fail open per crate: if a dependency cannot be safely rewritten, compile it unmodified and say so in the plan |
| R17 | **Security: telemetry exfiltration of secrets** | **Critical** | Recording arguments by default would send passwords, tokens, and PII to a telemetry backend that nobody audited | `skip_all` unconditionally in Phase 1. Argument capture is opt-in, per-rule, and never a default. Document this as a security property, not a limitation |
| R18 | **Instrumentation code panics** | **High** | A panicking `Debug` impl invoked from injected code turns a working program into a crashing one | Do not format user values (R17 already ensures this). Do not use `catch_unwind` as a crutch — it is a no-op under `panic=abort` |
| R19 | **eBPF portability (future)** | **Medium** (deferred) | Kernel version floors, `CAP_BPF`/`CAP_SYS_PTRACE`/`CAP_NET_ADMIN`, lockdown mode, cgroup restrictions, and non-Linux platforms **[Fact]** | Out of scope until Phase 3. Ensure the compile-time tool never depends on eBPF being available |
| R20 | **The eBPF hypothesis (H2) is false** | **Medium** (project-scope risk) | If logical async spans cannot be reconstructed from poll events, the project's novel research claim evaporates | Architecture A has standalone value. Treat H2 as an experiment with a scheduled go/no-go (§15.6), not as a planned deliverable |
| R21 | **Scope creep into eBPF during Phase 1** | **High** (project risk) | It is the most interesting part and will pull attention away from a shippable tool | Written scope boundary in §12.3. No eBPF dependency may enter the repository before the MVP success criteria are met |
| R22 | **`otelc` or the OTel Rust SIG ships this first** | **Low-medium** | Rust is the conspicuous gap on the zero-code list; someone will fill it | Not a reason to hurry into bad architecture. If it happens, contributing to that effort is a better outcome than competing. Re-check the SIG's status before Phase 2 |
